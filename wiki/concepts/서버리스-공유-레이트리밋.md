# 서버리스 공유 레이트리밋

> Upstash Redis REST 파이프라인(INCR + PEXPIRE NX + PTTL) 고정 윈도우 카운터 + 인메모리 폴백. 서버리스에서 인스턴스별 인메모리 리미터는 무용지물이라 공유 저장소가 필수.

## 무엇 / 언제 쓰나
Vercel/Lambda 등 서버리스에 로그인·공개 쓰기 엔드포인트 레이트리밋을 붙일 때. SDK 의존성 없이 `fetch`만으로 동작.

## 정본 구현 (canonical)
- `_wiki/raw/snapshots/massage/src/lib/security/rate-limit.ts:204` — `checkSharedRateLimit`: REST `/pipeline`으로 `INCR`→`PEXPIRE NX`(첫 증가에만 TTL)→`PTTL`, `AbortSignal.timeout(2s)`, 실패 시 `null` 반환해 인메모리로 폴백.
- `_wiki/raw/snapshots/massage/src/lib/security/rate-limit.ts:164` — `findPrefixedRestConfig`: Vercel 마켓플레이스가 붙이는 커스텀 접두사(`<prefix>_KV_REST_API_URL`) env를 접미사 매칭으로 탐색. 표준 이름 하드코딩하면 프로드에서 연결 실패함(실사례).
- `_wiki/raw/snapshots/massage/src/lib/security/rate-limit.ts:39` — `getClientIp`: 플랫폼 헤더(`x-real-ip`/`x-vercel-forwarded-for`/`cf-connecting-ip`) 우선 — `x-forwarded-for` 좌측값은 클라이언트 위조 가능.
- `_wiki/raw/snapshots/massage/src/lib/security/rate-limit.ts:60` — `createMemoryRateLimiter`: 만료 버킷 주기 스윕 포함 폴백/테스트용.

## 다른 구현 / 변형
- IP 버킷 + 크리덴셜 버킷 이중 키: `rate-limit.ts:257` `buildAuthRateLimitKey` (routeKey:IP[:credential]).

## 주의점 / 함정
- 응답 헤더에 `X-RateLimit-Scope: shared|instance`를 넣어 프로드에서 어느 경로가 작동 중인지 관측 가능하게 할 것 (`rate-limit.ts:199`).
- Redis 장애 시 폴백은 "인스턴스별"이라 한도가 사실상 N배로 풀림 — 보안 민감 경로면 폴백 시 로깅 필수.
- **리미터 도입 = 자기 통합테스트 파괴 (BAGJO1 2026-07-18 실사례).** 주문 생성에 IP 키 5건/60s를 붙이자(`BAGJO1/src/lib/orders/rateLimit.ts:28` `checkOrderRateLimit`) 결제 통합 스펙이 한 CI 러너 IP로 주문 6+건을 만들며 **자기 트래픽만으로 429** — 오버셀 스펙의 패자가 409(재고 경합) 대신 429를 받아 2연속 CI 실패. Vercel은 엣지에서 `x-forwarded-for`를 덮어쓰므로(`rateLimit.ts:47` 주석) 스펙이 헤더로 키를 회전시키는 우회도 불가. 해법 = 스펙 측 창 리셋 재시도: `BAGJO1/tests/payments/payment-routes.spec.ts:31` `callApi`가 POST 대상 429 시 61s 대기 후 1회 재시도 + `test.info().setTimeout` 연장(단언 강도 불변). **리미터를 넣는 PR에서 통합 스펙의 요청 총량/창 관계를 같이 설계할 것.**
