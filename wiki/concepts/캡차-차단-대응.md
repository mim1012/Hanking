# 캡차 / 차단 감지 & 대응

> 영수증 캡차·보안페이지·429·Cloudflare 챌린지를 감지하고 대응(Vision 솔버/대기/재시도). 트래픽 봇 공통.

## 무엇 / 언제 쓰나
자동화 중 캡차·차단 신호가 나타날 때 감지→분류→대응. "IP 차단으로 단정 금지" 규칙 포함.

## 주의점 / 함정
- `ANTHROPIC_API_KEY` 캡차 보조는 electrone·sellermate 공통.
- **캡차 체이닝**: 하나를 정답으로 풀어도 곧바로 다른 문항의 캡차가 이어서 뜬다. 단발성 solve-then-verify로는 못 뚫는다 — 최대 N라운드 재시도 루프 필수(sellermate 사례: 5라운드).
- **코드 존재 ≠ 실제 배선**: 캡차 솔버 파일이 서버에 있어도 호출부에서 안 부르면(구버전 코드 드리프트 등) 무용지물. `ANTHROPIC_API_KEY`가 `.env`에 실제로 있는지도 별도 확인(있어야 할 것 같은데 없었던 사례 — sellermate 4대 서버 전부).
- **네이버 하드차단(418)의 진짜 트리거는 "레퍼러 없는 URL 직행"이지 IP 평판이 아니다** — sellermate 2026-08-15: 완전히 다른 3개 IP(로컬 ISP·SSH SOCKS 프록시·상용 유동IP 프록시풀)로 검색 URL에 직접 `page.goto()`했더니 전부 동일하게 즉시 418("짧은 시간 내 너무 많은 요청"/"VPN을 사용하여 접속한 IP"). 메인 페이지→검색창 타이핑→클릭으로 자연스럽게 진입하면 같은 IP·같은 세션에서도 하드차단은 피하고 정상 캡차 단계로만 감. → `turafic/CLAUDE.md`의 "IP차단으로 단정 금지" 규칙을 한 단계 더 구체화: 반복 차단이 보이면 IP를 의심하기 전에 **URL 직행 경로부터 점검**.

## 배제된 접근 (dead-end)
- **IP 로테이션만으로 하드차단 해결 시도** — sellermate 2026-08-15: 로컬 IP가 418 차단된 상태에서 SSH SOCKS 프록시로 완전히 다른 IP(SK브로드밴드)로 우회했으나 동일하게 즉시 차단. 상용 유동IP 프록시(CoolIP)로 또 다른 IP로 재시도해도 동일 결과. **3개의 서로 다른 IP가 전부 실패**했다는 게 "IP 문제가 아니다"의 직접 증거 — URL 직행 패턴을 자연 네비게이션으로 바꾸고 나서야 하드차단이 사라짐(위 함정 항목 참고).
