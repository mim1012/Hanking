# 멀티테넌트 요청 파이프라인

> 한 코드베이스로 여러 테넌트를 서빙. Guard→TenantMiddleware→ResponseInterceptor 파이프라인 + organizationId 격리.

## 무엇 / 언제 쓰나
SaaS를 도메인/조직별로 격리 서빙할 때. 두 가지 접근(미들웨어 라우팅 vs 테넌트 스코프 쿼리).

## 정본 구현 (canonical)
- **NestJS 테넌트 파이프라인** — `medical-ERP-/apps/api/src/common/` — `SupabaseAuthGuard`(JWT→user) → `middleware/tenant.middleware.ts`(request.organizationId) → `interceptors/response.interceptor.ts`(`{success,data,meta}` 표준) → `HttpExceptionFilter`. 스키마 `apps/api/prisma/schema.prisma:17` `Organization`+`Plan` enum, 모든 모델 FK+`@@index`, RLS via Supabase.

## 다른 구현 / 변형
- **Next.js 미들웨어 라우팅** — `adpang-production/middleware.ts` — host 정규화(`x-forwarded-host`, `www.` 제거)로 테넌트 감지 → glossy/sellermate/quickslot 라우팅 + HTML meta/favicon `ReadableStream` 리라이트. 격리는 `distributor` 스코프.

## 주의점
- 모든 Prisma 쿼리에 organizationId 필터 강제(medical). adpang은 단일 DB 공유 + distributor 스코프.
