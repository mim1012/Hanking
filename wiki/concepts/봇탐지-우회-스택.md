# 봇탐지 우회 스택 (핑거프린트 스푸핑 / 스텔스)

> 브라우저 자동화 시 봇 탐지를 회피하는 5계층 기법 — Network/Browser/Device/Session/Behavior.

## 무엇 / 언제 쓰나
Patchright/Playwright/Selenium으로 네이버·쿠팡·Cloudflare 사이트를 자동화할 때. 하드코딩 UA 금지, 실제 브라우저 지문과 일치시켜야 탐지 안 됨.

## 정본 구현 (canonical)
- **모바일 스텔스** — `electrone_navershopping/shared/mobile-stealth.ts` — 실제 시스템 Chrome 버전 + GREASE brand 동적 감지(`detectRealChrome:44`), CDP UA/Client-Hints 오버라이드(`setupMobileCDP:97`), navigator/webGL(Adreno)/battery/webdriver 오버라이드 스크립트(`MOBILE_STEALTH_SCRIPT:152-305`).
- **5계층 명세** — `electrone_navershopping/CLAUDE.md:51-59`.

## 핵심 통찰 (함정)
- 하드코딩 `sec-ch-ua`가 TLS fingerprint 실제 버전과 불일치하면 즉시 탐지됨 (`mobile-stealth.ts:39-43`).
- 네이버는 high-entropy 헤더를 Accept-CH로 요청하지 않으므로 제거해야 함 (`:337-340`).
  **2026-08-03 와이어 재확인**: 요청하지 않는 것이 맞다. 다만 예전에는 `sec-ch-ua-model: ""` 처럼
  **빈 값으로 붙어 나가는** 상태였고 그게 더 나쁘다(실물에서 나올 수 없는 모양).
- esbuild 번들 코드를 `page.evaluate`에 넣을 땐 `__name` 폴리필 필수 (`electrone_navershopping/CLAUDE.md:113-119`).
- **Android WebView 는 `X-Requested-With: <앱 패키지명>` 을 모든 요청에 붙이고, 앱이 이를 막을 수 없다.**
  진짜 브라우저는 이 헤더를 보내지 않으므로 UA/sec-ch-ua 를 아무리 맞춰도 이 하나로 "앱 안 웹뷰"가 드러난다.
  특히 UA 가 독립 브라우저(SamsungBrowser/Chrome)를 주장하면 **성립 불가능한 조합**이 된다.
- **「로그만 성공인 억제」** — `WebSettingsCompat.setRequestedWithHeaderOriginAllowList()` 는 값을 저장하고
  getter 로 되읽히기까지 하지만 **헤더는 그대로 나간다**(아래 dead-end). 코드·로그만 보면 완벽해 보인다.

## 검증 방법 (Android WebView)
- **헤더 에코 페이지 원샷** — 봇 WebView 에 `https://httpbin.org/headers` 를 띄우고 `screencap` 을 읽으면
  메인프레임 요청 헤더 전체가 한 화면에 나온다. 프록시·CA·터널 전부 불필요, 몇 초.
  `naver_turafic_samsung/android/SamsungTrafficBot/app/src/main/java/com/navertraffic/samsung/ui/MainActivity.kt:275`
  `enterDebugBrowserMode()` — 인텐트 키 `debugUrl`(`:2215`). 페르소나만 적용하고 **작업 루프·원격제어를
  타지 않아** 프로덕션 큐도 계정도 건드리지 않는다.
- mitmproxy 전수 캡처는 **여러 홉을 한꺼번에** 볼 때만. 단일 홉 헤더 확인에는 과하고 실제로 더 나빴다(dead-end).

## 배제된 접근 (dead-end)
- **`setRequestedWithHeaderOriginAllowList(emptySet())` 로 X-Requested-With 제거** — 실측 반증(2026-08-03,
  SM-G930K / WebView=Chrome 138). 가설 3개 중 "호출 안 됨"·"기능 미지원"은 로그로 반증됐고
  (`XRW-SUPPRESS: applied, allowList=[]`), 결정적으로 **우리와 무관한 오리진 하나만** 허용목록에 넣어도
  (`[https://xrw-probe.invalid]`) 헤더가 그대로 나갔다 → "빈 목록 = 제한 없음" 해석 문제가 아니라
  **허용목록 자체가 강제되지 않는다.**
  구현: `naver_turafic_samsung/android/SamsungTrafficBot/app/src/main/java/com/navertraffic/samsung/strategy/SamsungWebViewManager.kt:1334`
  `suppressRequestedWithHeader()` (호출은 `:1350`). 코드는 남겼으나 **효과 없음**을 주석에 명시.
  같은 함정에 `zero-android-optionc/app/src/main/java/com/zero/traffic/service/TrafficService.java:300` 도
  빠져 있다(`"★ X-Requested-With 제거 완료"` 로그만 찍힘) — **베껴올 해법이 없다.**
  남은 길: 패키지 개명(값만 바뀌고 모순은 남음 + OTA 로 못 넘어감) / `shouldInterceptRequest` 재발행(무거움) /
  최신 WebView 재측정.
- **단일 홉 헤더 확인에 mitmproxy 리그** — 시스템 CA·adb reverse·포트 충돌·프로세스 2개를 거쳐 5MB 를 잡고도
  **메인프레임 요청이 0건**이었다. 헤더 에코 페이지가 더 정확하고 100배 싸다.
