# 레거시 코드체계 호환 필터

> 분류 코드 체계가 바뀐 뒤(예: 광역 `gyeongsang` → 도시 `busan`) 운영 DB에 신·구 값이 공존할 때, 필터는 exact match 대신 variant IN-list로 조회해야 한다. massage 환불 사고(2026-07-05)의 직접 원인이자 해법.

## 무엇 / 언제 쓰나
지역·카테고리·상태값 등 enum성 컬럼의 명명 체계를 마이그레이션 없이 바꾼 모든 프로젝트. "새로 등록한 항목이 필터에 안 잡혀요"는 십중팔구 이 문제다.

## 정본 구현 (canonical)
- `_wiki/raw/snapshots/massage/src/lib/region-compat.ts:3` — `getRegionVariants(region)`: 선택 코드 + 레거시 매핑 코드를 배열로 반환 → Prisma `{ region: { in: variants } }`.
- `_wiki/raw/snapshots/massage/src/lib/region-compat.ts:12` — `matchesRegion(candidate, selected)`: 클라이언트 측 목록 비교용 동일 규칙.

## 다른 구현 / 변형
- 서버 쿼리 적용부: `_wiki/raw/snapshots/massage/src/lib/server/communityStore.ts` 관리자 목록/페이지/옵션 쿼리 (커밋 `beeb953`).

## 주의점 / 함정
- **화면(공개/관리자/프리미엄)마다 필터를 따로 구현하면 반드시 한 곳이 깨진다.** massage에서 공개는 호환 처리, 관리자는 exact match로 남아 부산 업소가 관리자에서만 사라짐 → 환불. 공유 헬퍼 하나로 강제할 것.
- 클라이언트에서 코드를 변환해 보내지 말 것(부산→gyeongsang 변환이 사고 원인). 선택값 그대로 보내고 서버가 variants를 확장.
- **테스트 픽스처에 신·구 값 혼합 데이터를 시딩**해야 회귀가 잡힌다. 깨끗한 픽스처는 이 버그를 통과시킨다 (massage 테스트 90+개가 못 잡은 이유).
- 근본 해결은 데이터 마이그레이션(구코드→신코드 일괄 UPDATE + 매핑 제거)이며, 이 헬퍼는 그때까지의 호환층.
