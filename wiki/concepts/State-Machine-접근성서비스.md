## 주의점 / 함정
- **수락 완료 오판과 정지 누락 (Vortex, 2026-09-14)** — 탭 문구는 비선택 상태에서도 존재한다. 실제 수락/확인 입력 이후 선택된 목적 화면을 판정하고 실패 다이얼로그를 우선해야 한다. `Vortex/app/src/main/java/com/example/twinme/domain/state/handlers/WaitingForConfirmHandler.kt:153`. 성공 후 다음 root 조회를 기다리지 않고 즉시 정지해야 화면 전환으로 root가 사라져도 멈춘다: `Vortex/app/src/main/java/com/example/twinme/engine/CallAcceptEngineImpl.kt:357`. Android 기기 테스트에서 지연 완료 방식의 실패와 즉시 완료 방식의 통과를 확인했다.
- **"무시(ignored)"와 "거절(rejected)"이 같은 accepted=false로 보여도 다운스트림 액션이 다르다 (Vortex, 2026-09-15)** — 증상: 출발임박 배지 맞춤콜이 거절 클릭 없이 맞춤 목록에 남아 매 사이클 재감지. 원인: 적격성 판정기 `Vortex/app/src/main/java/com/example/twinme/domain/model/CallEligibilityDecision.kt:41-52`의 임박 분기가 맨 앞에서 `ignored`로 조기 리턴해, 뒤의 맞춤콜 경로(능동 거절)를 굶겼다. `Vortex/app/src/main/java/com/example/twinme/domain/state/MatchCallRejectionPolicy.kt:9-15`는 `!accepted && !ignored`일 때만 거절을 지시한다. 기법: 3상태(수락/거절/무시) 판정기에서 "무시"는 능동 액션이 필요한 항목(맞춤콜처럼 큐에 남는 것)에 절대 쓰지 말고, 분기 추가 시 정책 객체의 기대 액션까지 테스트에 박는다(`CallEligibilityDecisionTest.imminentMatchCall*`). 수락은 비가역 커밋이라 애매하면 거절이 fail-safe. 경쟁앱 오버런도 이 결합케이스는 거절 없이 새로고침만 한다(`Vortex/apk_extractor/overun-tuto/jadx-single/sources/com/overun/tuto/AdvancedMacroService.java:488-534`).
- **탭 결과가 원격로그에만 남으면 "탭 안 나감"과 "탭은 나갔는데 외부요인"을 못 가른다 (Vortex, 2026-09-16)** — 증상: 수락 3단계(확인) 탭이 0% 성공, 확인창 도달 후 몇 초 뒤 콜취소. "3단계가 안 눌린다"로 오진할 뻔함. 원인: 수락 확인 dispatch 결과가 전부 `Vortex/app/src/main/java/com/example/twinme/domain/state/handlers/WaitingForConfirmHandler.kt`의 `logAcceptFlowOutcome`(Supabase 전송)으로만 남아, Supabase 자격증명이 빈 디버그 빌드에선 로컬 logcat에 **아무 흔적이 없었다**(반면 거절 경로는 `Log.i` 로컬 로그가 있어 매번 관측됨). 기법: 실기기 디버깅 전에 **판정 대상 경로가 원격 전용 로그인지부터 확인**하고, 그렇다면 dispatch 발사·재탭 보류·대기 진입에 로컬 `Log.i`를 먼저 심는다. 그리고 **작동하는 형제 경로(여기선 거절 확인)와 방식·재탭 전략을 비교**해 코드 탓으로 단정하기 전에 외부요인을 배제한다. 결론: 확인 탭은 `performAction(ACTION_CLICK)` attempt=1로 정상 작동(→CALL_ACCEPTED 실증), 앞선 실패는 전부 외부 콜취소였다. 재탭 로직도 이미 존재(다이얼로그 보이는 한 최대 8회 fall-through)했으므로 "한 번 누르고 마는 버그"라는 첫 가설은 코드 재독으로 반증됐다.
- **시스템 팝업이 대상 앱을 밀어내면 대상 앱을 재포그라운드로 복구 (Vortex, 2026-09-16)** — 증상: 긴급재난문자(`com.google.android.cellbroadcastreceiver`) 팝업이 뜨자 상태머신이 "다른 앱이 포그라운드"로 31분간 무한 대기(콜 검사 정지). `adb shell input keyevent 4`(BACK)로는 안 닫혔고, 안전 다이얼로그를 좌표 추측으로 탭하는 것은 금지. 복구: 안전 알림을 건드리지 말고 **대상 앱을 다시 포그라운드로 올린다** — `adb -s <S> shell monkey -p <target_pkg> -c android.intent.category.LAUNCHER 1` → 잔여 팝업 태스크가 밀려나며 즉시 정상 순환 복귀(05:30 실증). 재난문자는 재난문자함에 보존되므로 정보 손실 없음. 헬스체크가 "다른 앱이 포그라운드/cellbroadcast"로 도배되면 이 복구를 적용. dead-end: BACK 키·좌표 탭.
- **파싱 시점 좌표를 탭 시점에 재사용하면 재렌더로 엉뚱한 항목을 탭 (Vortex, 2026-09-16)** — 증상: 초 단위로 재정렬되는 맞춤콜 리스트에서, ANALYZING 때 얼린 `eligibleCall.bounds`(주로 FastTree 별도 프로세스 스냅샷) 중앙을 CLICKING_ITEM에서 재조회 없이 탭 → 그 사이 최상단이 다른 콜로 바뀌면 **엉뚱한(더 비싼) 콜**을 누른다(사용자 리포트 "엉뚱한 곳 누름"). 원인·수정 지점: `Vortex/app/src/main/java/com/example/twinme/domain/state/handlers/ClickingItemHandler.kt:249`(수정 전 stale 좌표 탭). 기법: **탭 직전** 현재 창에서 a11y(`vg_item`)→FastTree로 최상단 항목을 **fresh 재조회**하고, 파싱 시점 항목과 **identity(가격+경로) 대조** — 경유지 유무로 파서마다 `split("→")` 방식(제한/무제한)이 달라 dest 문자열이 어긋나므로 **정확일치 OR 한쪽이 다른 쪽으로 `startsWith`**의 관용비교로(안 그러면 같은 콜을 불일치로 오판→무한 재분석 livelock). 불일치/판독불가면 **스테일 좌표를 절대 탭하지 말고 재분석으로 클린 실패**(MAX_REVALIDATE_RETRY 후 abort). 매직 픽셀 오프셋은 넣지 말 것(freshness가 답이지 해상도 의존 매직넘버가 아님). 스테일 노드 폴백(`clickableNode.performAction`)도 RecyclerView 리바인딩으로 다른 행을 가리키니 제거. 경쟁앱 2종이 동일 철학: touchassist `revalidateFirstCardBeforeInlineTap`(`android-decompile/touchassist/jadx/sources/com/kakaotaxi/reserve/auto/accessibility/ReservationWatchService.java:30346`, fresh 재프로브→시그니처 대조→불일치 abort), overun `getIteminFirstPosition`(`Vortex/apk_extractor/overun-tuto/jadx-out/sources/com/overun/tuto/runcase/MacroCase1Reject.java:420`, 탭 순간 `tv_reserved_at` fresh 읽고 탭). S25U 실증: 실제 재정렬 오탭 2건 차단(오탐 0). 좌표 신선도/관용비교는 순수함수로 떼 단위테스트.
- **고정 settle을 제거해 속도를 얻되 ceiling backstop으로 회귀 방지 (Vortex, 2026-09-16)** — 증상: 맞춤콜 거절 첫 탭 전 무조건 700ms 대기라 느림. 기법: 700ms 고정 → (짧은 floor + 버튼 좌표가 직전 틱과 ±8px 안정) **또는** (600ms ceiling 초과)면 탭. ceiling backstop이 핵심 — 3.0.4 버튼 jitter로 좌표가 안 잡혀도 결국 탭을 보장해 **기존 700ms보다 절대 느려지지 않게** 한다(안정 dwell만 두면 안 멈추는 버튼에서 8초 타임아웃으로 오히려 퇴보). `Vortex/app/src/main/java/com/example/twinme/domain/state/handlers/DetectedCallHandler.kt`의 `handleMatchCallRejection` + 순수 `shouldFirstRejectTap`(단위테스트). 정직한 한계: 수락 STEP2의 `MIN_INTER_STEP` 축소는 실측상 병목이 버튼 등장/ready라 이득이 좁다(fast-tail만).
- **리스트 레벨 "맞춤 N건" 배지를 개별 콜 속성처럼 써서 콜타입 필터를 우회 (Vortex, 2026-09-17)** — 증상: 일반/1시간 예약만 받게 해놨는데 **12시간 대절(270,000원)이 수락됨**. 원인: `ReservationCall.isMatchCall`은 개별 콜 속성이 아니라 리스트에 "맞춤 N건" 배지가 있으면 붙는 **리스트 레벨 플래그**다(기본값 false `Vortex/app/src/main/java/com/example/twinme/domain/model/ReservationCall.kt:76`, true로 세팅되는 곳은 리스트배지 감지 둘뿐 — `Vortex/app/src/main/java/com/example/twinme/domain/state/handlers/AnalyzingHandler.kt:271-277`의 `isMatchCallList`(`:513-525`, `tv_total_count`의 "맞춤 N건" N>0) + `Vortex/app/src/main/java/com/example/twinme/domain/state/handlers/CallListHandler.kt:51`). 그런데 적격성 판정 `Vortex/app/src/main/java/com/example/twinme/domain/model/CallEligibilityDecision.kt:70`이 `if (!isMatchCall && !isAcceptableCallType())`라 **맞춤콜이면 콜타입 게이트를 통째로 건너뛰어서**, 맞춤 섞인 리스트의 최상위 12시간 대절이 콜타입 필터를 우회하고 금액(270,000≥minAmount)만으로 수락됐다(CALL_LIST 개별평가 eligible=false → 최상위 재분류 후 eligible=true 뒤집힘이 시그니처). 기법: `!isMatchCall &&`를 제거해 **콜타입 게이트를 맞춤콜에도 적용** → 일반/1시간(토글 ON)만 통과, 그 외 시간제는 맞춤 여부 무관 거절. `isAcceptableCallType`(`CallEligibilityDecision.kt:99-103`)는 "일반 예약" 항상 허용 + `(?<!\d)1시간` 정규식으로 1시간만(11/12/21시간 substring 오탐 방지) 토글 시 허용. 기존 맞춤콜 테스트가 전부 callType="일반 예약"이라 회귀 없음 확인 후 제거. 회귀테스트 `CallEligibilityDecisionTest.matchCallWith12HourReservationIsRejectedNotAccepted` 외 예약콜·맞춤콜 콜타입 매트릭스(총 30개 통과). 실기기 실증(S25U 2.9.0-debug): 맞춤콜 재분류돼도 `eligible=false`로 거절(자동수락 안 됨), 예약콜은 `조건 충족`(=콜타입 게이트 통과 이후에만 찍힘)까지 도달 후 수락. **일반화 교훈: 리스트 전체에 붙는 배지/카운트를 개별 항목 속성으로 취급하면 오분류되고, 그 플래그로 필터를 우회시키면 원치 않는 타입이 통과한다 — 배지는 "이 리스트에 X가 있다"지 "이 항목이 X다"가 아니다.**
