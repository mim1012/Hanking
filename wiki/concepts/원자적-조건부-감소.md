# 원자적 조건부 감소 (오버셀/더블스펜드 방지)

> 락 없이 `updateMany({where:{...gte}, data:{decrement}})` + `count` 검증으로 재고·포인트 동시 차감의 오버셀/더블스펜드를 막는 패턴. dorami 최고의 재사용 자산.

## 무엇 / 언제 쓰나
재고 차감, 포인트 사용, 쿠폰 소진 등 "잔량이 충분할 때만 원자적으로 줄여야" 하는 모든 곳. 비관적 락(SELECT FOR UPDATE) 없이 ReadCommitted에서 안전.

## 정본 구현 (canonical)
- **포인트 차감** — `dorami/backend/src/modules/points/points.service.ts:250` `deductPointsTx` (canonical, 2026-07-07 재검증) — `updateMany({ where:{ userId, currentBalance:{ gte:amount } }, data:{ currentBalance:{ decrement:amount } } })`(`:266`), `updated.count===0`이면 원인 조회 후 `INSUFFICIENT_POINTS`(`:279`). WHERE의 `gte` 재검사가 커밋값에 재평가돼(주석 `:261`) 동시 사용자의 loser가 행 락에서 재평가 후 0행 매치 → 더블스펜드 방지. 적립은 `addPoints`가 `increment`로 원자적.

## 다른 구현 / 변형
- **재고 차감은 이 패턴을 버리고 비관적 락+clamp로 갔다 (2026-07-07 설계 반전)** — dorami 재고는 예전 `inventory.service.ts` `batchDecreaseStockTx`(`updateMany({where:{quantity:{gte}}, decrement})`, 주문 *생성* 시점, 부족하면 throw)를 **삭제**하고 `inventory.service.ts:34` `batchConfirmDecreaseStockTx`로 교체 — **결제 *확정* 시점에 `SELECT … FOR UPDATE`(`:55`/`:64`) 선취득 + `Math.max(0, …)` clamp**(`:116`)로 전환. 이유: 미결제 주문이 재고를 잡지 않게 하려는 비즈니스 결정(unpaid orders hold no stock, oversell 명시 허용). 즉 "잔량 가드가 필요한 곳"(포인트)엔 이 낙관적 패턴이, "미결제는 재고 미점유 + 확정시 1회 감소"가 필요한 곳(재고)엔 비관적 락+clamp가 맞는다는 tradeoff 사례. 상세는 [[project-dorami]] 동시성 절.

- **Postgres RPC로 원자화 + 판단/실행 분리 (BAGJO1 결제, 2026-07 프로덕션)** — 재고 감소/복원을 앱 코드가 아니라 DB 함수(`BAGJO1/supabase/migrations/0021_decrement_stock_for_order.sql`·`0023_restore_stock_for_order.sql`, 취소·데드레터 회수도 0024/0025/0027 RPC)로 내려 원자성을 확보하고, "무엇을 할지"는 순수 함수 `src/lib/payments/decide.ts`가 결정 — 복원 액션(`restoreConfirming`)은 브랜디드 타입(`:58` 비공개 심볼)이라 decide를 거치지 않고 구성 불가 → "관찰이 불명이면 취소/복원 금지"가 타입 수준 불변식. 상세 [[project-BAGJO1]].

## 함께 쓰는 동시성 기법 (dorami)
- **다건 락 순서 정렬로 데드락 방지** — 재고 재설계로 `inventory.service.ts:41`(`sortedItems`)→`:55`/`:64`(`SELECT id … ORDER BY id FOR UPDATE`)로 이동. productId→variantId 오름차순 정렬 후 락 선취득(두 확정이 항상 같은 순서).
- **재시도 트랜잭션 밖에서 ID 생성** — `orders.service.ts:155` — orderId를 tx 밖에서 1회 생성해 재시도 시 시퀀스 갭/중복 방지(`:150` 주석). `withOrderTransactionRetry`(P2034/P2028 재시도, `:157`).
- **예약번호 Redis INCR 원자 채번** — `reservation.service.ts:83` + `@@unique([productId, reservationNumber])`.

## 배제된 접근 (dead-end)
- **모킹 유닛테스트로 raw-SQL 검증** — 재고 FOR UPDATE 락의 `$queryRaw`가 Prisma 모델명(`"Product"`)을 써서 실 snake_case 테이블(`products`)을 못 찾은 42P01 버그(`e5e685b1`)를 모킹 유닛테스트는 못 잡았다(`tx.$queryRaw` stub → SQL 문자열 미검증). 실DB 통합/스테이징 검증이 필수. 상세 [[project-dorami]] "raw SQL 테이블명 드리프트" 교훈.
