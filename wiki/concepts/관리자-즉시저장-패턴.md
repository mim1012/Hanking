# 관리자 즉시저장 패턴 (2단계 저장 함정 제거)

> 관리자 CRUD 화면에서 등록·수정·삭제를 클릭 즉시 DB에 반영하고, "마지막으로 DB와 일치했던 목록"을 별도로 추적해 미저장 드래프트가 다른 액션에 딸려 커밋되거나 동시 요청이 서로를 덮어쓰는 걸 막는 4중 방어 패턴.

## 무엇 / 언제 쓰나
"등록/수정 폼 → 상단의 별도 저장 버튼 → 그제서야 DB 반영" 같은 2단계(batch save) 구조를 가진 관리자 CRUD 화면. 사용자가 등록·수정한 뒤 저장 버튼을 누르지 않고 나가거나, 삭제만 하고 다른 미저장 편집을 남겨둔 채 새로고침하면 "방금 한 작업이 없었던 일이 된다"는 실사용 데이터 유실 버그가 생긴다. 이 패턴은 등록·수정·삭제 세 액션 전부를 클릭 즉시 저장으로 바꾸고, 그 과정에서 필요해지는 3가지 레이스를 방어한다.

## 정본 구현 (canonical)
- `BAGJO1/src/app/admin/notices/page.tsx`(PR #140/#141/#149/#156 계보, 2026-07-18 확정) — 4개 방어 장치가 한 컴포넌트에 모두 존재:
  1. **`persistedItemsRef`**(`:83`) — "마지막으로 DB와 일치한 목록"을 `useRef`로 별도 보관. `handleCreate`/`handleUpdate`/`handleDelete`(`:119`·`:137`·`:156`) 전부 현재 화면 draft(`items` state)가 아니라 이 ref 기준으로 `nextItems`를 계산해 저장한다 — draft를 기준으로 저장하면 다른 미저장 편집이 이 액션에 딸려 함께 커밋되기 때문(예: 삭제 버튼 하나 눌렀는데 편집 중이던 다른 행까지 저장됨). 저장 성공 시에만 `persistedItemsRef.current`와 화면 draft를 함께 갱신해 둘을 계속 일치시킨다.
  2. **`busyRef`**(`:88`) — 등록·수정·삭제·저장 네 핸들러가 공유하는 상호배제 플래그. 각 핸들러 시작부에서 `if (!loaded || loadError || busyRef.current) return;` 가드 후 `busyRef.current = true` → try/finally로 `false` 복원. 저장 PUT이 in-flight인 동안 삭제를 누르면, 삭제가 persisted 기준 nextItems를 먼저 저장하고 뒤늦게 도착한 저장 PUT이 방금 지운 항목을 DB에 되살리는 레이스를 막는다.
  3. **loaded/loadError 게이팅**(`:76-80`, `:120`·`:138`·`:157` 가드절) — 초기 로드가 끝나기 전이나 로드 실패 시 저장을 아예 막는다. 이게 없으면 로드 완료 전 저장이 빈 값/기본값으로 DB를 덮어쓴다.
  4. **`ready` 콜백 게이팅**(`:111`, `onCreateRow={ready ? handleCreate : undefined}` 형태) — 로딩 중·실패 시 콜백을 아예 안 넘겨 `AdminResourcePage`가 버튼/UI 자체를 숨긴다. 콜백 내부 가드만으로는 버튼이 눌리는데 조용히 씹히는 무음 no-op이 된다.
- `BAGJO1/src/components/admin/AdminResourcePage.tsx` — `onSave` prop이 없는(=배치 저장 버튼이 없는) 화면에서는 생성폼/수정모달의 안내문구·버튼 라벨이 "저장하면 바로 반영됩니다."/"저장"으로 자동 전환된다(onSave 유지 화면과 하위호환).

## 다른 구현 / 변형
- `BAGJO1/src/app/admin/reviews/page.tsx` — 동일 4중 방어, 단 마지막 1건 삭제 차단 가드가 없다(전시 후기는 빈 목록을 정당한 상태로 허용 — notices는 "공지 0건"을 막는 별도 가드가 `handleDelete` 안에 있다).
- `BAGJO1/src/app/admin/concerns|kits|partners|insurance-content/page.tsx`(PR #141, 2026-07-18) — 같은 4중 방어를 4개 설정형 화면에 동시 적용한 배치 작업. notices/reviews와 도메인 모양(단일 배열 vs 여러 config 섹션)이 달라 세부는 다르지만 persistedRef+busyRef+게이팅 골격은 동일.

## 주의점 / 함정
- **"삭제 안 됨"·"수정 유실" 사용자 리포트 2건이 이 패턴을 낳았다(2026-07-18)** — 원래는 등록·수정만 draft에 반영되고 상단 배치 저장 버튼을 눌러야 DB에 반영되는 구조였는데, 삭제만 즉시저장으로 먼저 고쳤을 때(중간 단계) "저장 버튼을 안 누르고 나가면 등록/수정이 사라진다"는 문제가 여전히 남아 있었다 — 결국 등록·수정도 즉시저장으로 통일해야 종결됐다(부분 수정은 반쪽짜리 방어).
- **draft 기준 저장의 함정** — persistedItemsRef 없이 `items`(화면 draft) 기준으로 삭제를 저장하면, 편집 중이던 다른 행의 미저장 변경까지 그 삭제에 딸려 조용히 커밋된다. opus 리뷰 MEDIUM-1로 발견.
- **동시 PUT 부활 레이스** — busyRef 없이 저장·삭제를 병렬 허용하면, 늦게 도착한 저장 응답이 먼저 반영된 삭제 결과를 덮어써 지운 항목이 DB에 되살아난다. codex 2차 리뷰 HIGH로 발견 — 소스-계약 테스트(문자열 assertion)로는 이 타이밍 버그를 못 잡고, 실제 리뷰가 코드 흐름을 추적해서 찾았다.
- **소스-계약 테스트는 이 클래스 버그를 못 잡는다** — [[골든플로우-실구동-게이트]] 참고. 209개 문자열 assertion 테스트가 전부 통과한 채로 "삭제 안 됨" 버그가 배포됐다.

## 배제된 접근 (dead-end)
- **삭제만 즉시저장으로 먼저 고치고 등록·수정은 배치 저장 유지** — 2026-07-18 중간 커밋에서 시도(PR #140/#149 사이). "삭제했는데 되살아난다"는 즉시 안 잡히지만 "등록/수정했는데 새로고침하면 사라진다"는 리포트가 곧바로 재발했다 — 세 액션을 한 번에 통일하지 않으면 사용자 입장에서 저장 규칙이 액션마다 달라 예측 불가능해진다. #145("설정형 화면 삭제 즉시 저장" 잔여분)를 거쳐 최종적으로 세 액션 전부 즉시저장으로 수렴.
