# 서버리스-응답후작업-after
> Vercel/서버리스 라우트에서 "응답 보낸 뒤 실행할 백그라운드 작업"(메일 발송·로깅·후처리)은 순수 fire-and-forget이면 함수 동결로 조용히 유실된다. `next/server`의 `after()`(또는 `waitUntil`)로 런타임이 완료를 보장하게 해야 한다.

## 무엇 / 언제 쓰나
- API 라우트가 응답을 먼저 돌려주고 **그 뒤에** 부수효과를 실행해야 할 때: 이메일 발송(가입 인증·비밀번호 재설정), 알림, 분석 로깅, 캐시 워밍, 웹훅 후처리.
- 특히 응답을 **블록하면 안 되는**(사용자 대기 시간·타이밍 채널 방지) 작업. 예: 이메일 열거 방지를 위해 회원 존재 여부와 무관하게 즉시 200을 반환하고 메일은 뒤에서 보내는 패턴.
- 런타임: Vercel Functions/Fluid Compute 등 **응답 후 인스턴스를 동결/재활용**하는 서버리스. 장수 프로세스(로컬 `next dev`, 자체 호스팅 node)에서는 이 문제가 **드러나지 않는다** → 반드시 프로덕션에서 검증.

## 정본 구현 (canonical) — BAGJO1(백조오브제), 2026-07-10 프로덕션 검증
- `BAGJO1/src/app/api/members/password-reset/request/route.ts:39` — `after(async () => { 회원조회 → 스로틀 → createMemberToken → sendMail })` + 응답은 즉시 `200 {ok:true}`. 응답을 먼저 반환하므로 이메일 열거 타이밍 방어가 유지되면서도 메일 작업이 보장 실행된다.
- `BAGJO1/src/app/api/members/route.ts:88` — 가입(201) 후 인증 메일 발송을 `after()`로. 201 응답은 회원 insert만 마치면 즉시 나가고, 토큰 생성+메일은 응답 뒤.
- 공통 패턴: `import { after } from 'next/server'` → `after(async () => { try { ...await... } catch(e){ logServerError(...) } })`. `after` 콜백은 응답 실패(throw/redirect/notFound)에도 실행되며, 라우트의 `maxDuration` 안에서 돈다(Next 16 공식: node_modules/next/dist/docs/01-app/03-api-reference/04-functions/after.md).

## 주의점 / 함정
- **「서버리스 응답 후 fire-and-forget 유실」** — 순수 `void (async () => {...})().catch()`는 응답 전송 직후 함수가 동결되면 **첫 await에 도달하기도 전에 중단**될 수 있다. 유실은 조용하다(에러 로그조차 안 남음). BAGJO1에서 비밀번호 재설정 메일이 프로덕션에서 토큰조차 안 생기는 형태로 발현.
- **로컬에서 절대 안 드러난다** — `next dev`는 장수 프로세스라 백그라운드 프라미스가 끝까지 돈다. 코드 리뷰·로컬 스모크·유닛테스트 전부 통과해도 프로덕션에서만 깨진다 → **프로덕션 카나리로 부수효과의 실제 실행(예: DB에 토큰 row 생성)을 확인**해야 잡힌다.
- **왜 어떤 건 우연히 되나** — 응답 전에 무거운 `await`(예: DB insert)가 있으면 인스턴스가 잠깐 더 살아 백그라운드 작업이 운 좋게 실행될 수 있다(BAGJO1 가입 경로). 선행 await가 없으면(즉시 응답) 거의 확실히 유실. 이 "가끔 됨"이 진단을 흐린다 — 레이스이지 정상이 아니다.
- `after`는 request-time API가 아니라 라우트를 동적으로 만들지 않는다. 정적 페이지에서 부르면 빌드/재검증 시점에 실행됨.

## 배제된 접근 (dead-end)
- **순수 fire-and-forget `void (async...)().catch(log)`** — Next/서버리스 이전 습관. 장수 서버에선 맞지만 Vercel에선 응답 후 유실. BAGJO1이 이걸로 처음 배포했다가 프로덕션 카나리에서 재설정 메일 미발송 발견 → `after()`로 교체(PR #6). **로컬 통과 = 프로덕션 동작 아님**의 대표 사례.
- **응답을 블록해서 `await sendMail()`** — 유실은 막지만, 이메일 열거 방지(타이밍 균일)와 사용자 대기 시간을 해친다. 존재-여부에 따라 응답 지연이 갈리면 열거 오라클이 된다. 인증된 본인 요청(예: 로그인 상태의 verify/request)에선 허용 가능하나, 미인증 공개 엔드포인트에선 `after()`가 낫다.
- **외부 큐(SQS 등) 즉시 도입** — 베타 규모엔 과설계. `after()`로 충분하고, 대량 발송·재시도가 필요해지면 그때 큐로.
