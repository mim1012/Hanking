# 동시 클레임 랜덤화 (떼몰림 방지)

> 여러 워커가 동시에 "가장 오래 방치된 후보 1개"를 결정론적으로 클레임하면 전부 같은 후보로 수렴한다 — 상위 K개를 잠근 뒤 그중 1개를 무작위로 골라 분산시키는 패턴.

## 무엇 / 언제 쓰나
DB 기반 작업 큐/슬롯 클레임에서 `ORDER BY <최우선순위> LIMIT 1 FOR UPDATE SKIP LOCKED`처럼 "1순위 후보 1개"를 결정론적으로 뽑는 방식은, 동시 호출자가 적을 땐 공정한 라운드로빈처럼 보이지만 **호출자 수가 늘어나거나 폴링 간격이 짧아지면 전원이 같은 후보로 수렴**한다. 특히 그 후보가 외부 API의 레이트리밋 키(IP+상품ID 조합 등)와 연결돼 있으면, 여러 워커가 동시에 같은 키를 때려서 그 키 자체가 차단되는 자기파괴적 루프가 생긴다.

## 정본 구현 (canonical)
- `turafic_update/supabase-migrations/013-randomize-claim-slot-pick.sql:60-90` `claim_strategy_slot_group` — 대표 슬롯 선정을 `order by last_leased_at asc nulls first, id limit 1`(결정론적)에서, `with candidates as (... order by ... limit 20 for update of s skip locked) select ... from candidates order by random() limit 1`로 교체. CTE에서 상위 20개 후보를 먼저 잠근 뒤(SKIP LOCKED로 동시 트랜잭션과의 충돌은 그대로 방지) 그중 1개를 무작위로 선택. 시그니처·반환형은 그대로라 호출부(`scripts/strategy-a-runner.ts`) 수정 불필요.
- **실측 검증(2026-08-18)**: 배포 직전 2.5시간 — claim 231건이 slot 17개에 집중(1위 슬롯이 55건, 429 비율 85%, 성공률 0%로 붕괴). 배포 직후 1~2분 — claim 38건이 슬롯 38개 전원 서로 다름(중복 0). 배포 후 30분 재확인 — claim 60건에 distinct 슬롯 30개(1위도 12건 수준)로 안정적 분산 지속. Supabase REST(`strategy_slot_group_leases`)에서 `execution_slot_id`/`worker_id`/`created_at` 직접 집계로 대조.

## 다른 구현 / 변형
없음(같은 저장소 안에서만 확인). 다른 프로젝트에 유사한 "오래된 것부터 1개씩 클레임" 큐가 있으면(예: `[[요청-코얼레싱-인플라이트]]`류 인플라이트 관리) 이 패턴 이식 후보.

## 주의점 / 함정
- **"결정론적 순번 큐가 공정해 보이지만 동시성 아래선 떼몰림을 만든다"(named failure)** — `last_leased_at asc limit 1`은 단일 호출자 기준으로는 완벽한 라운드로빈이지만, N개 호출자가 짧은 간격으로 동시에 폴링하면 매 라운드 "지금 1순위"가 하나뿐이라 전부 거기로 몰린다. 이 저장소엔 이미 같은 계열의 named failure가 하나 더 있다 — [[project-turafic_update]]의 "슬롯≠MID 오매핑 쿨다운"(슬롯 단위 쿨다운이 MID 단위 레이트리밋을 못 막음). 둘 다 근본은 "여러 워커가 조율 없이 좁은 후보 풀을 공유"라는 같은 패밀리의 증상이며, 이번 건은 claim 시점의 선택 알고리즘 자체가 원인이라는 점이 다르다.
- CTE에서 잠근 상위 K개 중 나머지(K-1)개는 트랜잭션이 끝날 때까지 짧게 잠겨있다 — K를 너무 크게 잡으면 동시 클레임 처리량을 오히려 깎아먹는다. K=20은 실측 당시 유효 후보 풀(수십~수백 슬롯) 규모에 맞춘 값이라 다른 시스템에 이식 시 후보 풀 크기에 맞게 재조정 필요.
- 이 수정은 claim 시점의 "누가 어떤 슬롯을 잡는가"만 고친다. 클레임 이후 실행 결과 처리 로직(예: 실패 시 재격리 규칙)이 별도로 잘못돼 있으면 후보 풀 자체가 왜곡될 수 있다 — 같은 세션에서 `landing_keyword_pool.mid_verified`가 첫 실패부터 즉시 격리되던 별개 버그(007)도 같이 있었고, 이건 two-strike 정책(009/010)으로 별도 수정됨. 클레임 랜덤화만으로는 후보 풀이 부당하게 줄어드는 문제까지는 못 잡는다.

## 배제된 접근 (dead-end)
- **RPC가 한 번에 슬롯 N개를 배치로 반환하도록 바꾸기** — 처음 고려했으나 기각. 이 시스템은 워커(물리 PC) 1대당 브라우저 동시 실행 수가 1로 운영되고 있어서(플릿 429 대응으로 이미 하향 조정된 값), 호출자 각자가 폴링마다 슬롯을 딱 1개만 요청한다. 배치 반환은 "한 프로세스 안에서 여러 슬롯을 한 번에 받는" 경우에만 떼몰림을 줄이는데, 이 시스템의 떼몰림은 **서로 다른 물리 PC(프로세스)들이 각자 1개씩 요청하며 겹치는 것**이라 배치 반환으로는 근본 원인에 안 닿는다. 매 호출의 선택 자체를 확률적으로 분산시키는 이 방식이 실제 증상에 맞았다.
