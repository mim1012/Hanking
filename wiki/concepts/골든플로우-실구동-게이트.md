# 골든플로우 실구동 게이트 (3계층 테스트 모델)

> 소스-계약 테스트(항상, 초 단위)만으로는 "실제로 클릭했을 때만 드러나는" UX 버그를 못 잡는다는 실패에서, 변경 경로가 매핑된 도메인일 때만 실제 브라우저로 등록→수정→삭제까지 클릭하는 프리뷰 실구동 레이어를 추가한 3계층 CI 모델.

## 무엇 / 언제 쓰나
관리자 CRUD처럼 "화면에 값이 잘 뜬다"와 "그 값을 저장/삭제하는 상호작용이 실제로 동작한다"가 서로 다른 질문인 도메인. 순수 함수·타입·문자열 assertion 테스트는 빠르고 항상 돌지만 클릭 순서·타이밍 레이스·실제 렌더 결과를 검증하지 못한다. 매번 전체 e2e를 돌리면 무관한 PR까지 느려지고 DB 쓰기가 늘어나므로, "이 배포가 어떤 도메인 경로를 건드렸는가"로 실구동 스펙 실행을 게이팅한다.

## 주의점 / 함정
- **소스-계약 테스트 209개 통과 + 실버그 배포** — 2026-07-18 사고 원인: 관리자 "삭제 안 됨"·"수정 유실" 버그 2건이 문자열 assertion 테스트 209개를 전부 통과한 채 배포됐다. 아무 테스트도 실제로 화면을 클릭하지 않았기 때문 — 이 게이트가 만들어진 직접 계기.
- **e2e 구축 자체가 사고를 만나 새 실버그를 발견했다** — 실구동 스펙을 작성하는 과정에서 (버그를 찾으려던 게 아니라 스펙을 통과시키려다) 추가로 드러난 버그들: 공지가 홈 소식 위젯에 절대 안 뜨던 정렬 버그([[관리자-즉시저장-패턴]]과 별개, PR #144), 업로드 이미지가 `next/image` 허용 호스트 미등록으로 공개 상세 페이지 전체를 크래시시키던 버그(PR #153), 회원·보험 상세가 Next 16의 `params: Promise` 미해제로 생성 이래 한 번도 정상 동작한 적 없던 버그(PR #155, `admin/members/[id]`·`admin/insurance/[id]` 동일 클래스 전수 점검으로 같이 고침), 상품문의/구매평 작성 모달이 부모 리렌더마다 새 객체 리터럴로 리셋 effect가 재발화해 작성 중 입력이 소리 없이 증발하던 버그(PR #157, `src/components/inquiries/InquiryFormModal.tsx`·`src/components/shop/ProductTabsClient.tsx` + 스윕으로 발견한 동일 클래스 `src/components/reviews/ReviewFormModal.tsx`도 같이 수정, 2026-07-18 origin/main 머지 확인). 실구동 게이트를 "만드는 과정" 자체가 회귀 방지 그물 역할을 했다.
- **미해결 채로 남은 동일 클래스 버그 — concerns 목록** — `admin-crud-concerns.spec.ts:19-24`가 명시: 공개 `/concerns` 목록이 `concerns.slice(0, 8)`/`slice(8, 12)`로 앞 12건만 보여주는데 등록은 배열 끝에 append한다. notices와 완전히 같은 구조적 함정이지만 #144가 고친 건 notices뿐이라 concerns는 아직 살아있다 — 스펙이 이걸 검증하지 않고 주석으로 팀 리드에게 명시적으로 플래그만 해뒀다. "실구동 스펙을 쓰다가 발견했지만 그 자리에서 고치지 않고 이슈로 남긴" 사례.
- **e2e 하네스 자체의 버그도 실측으로 드러났다** — `admin-crud-products.spec.ts`의 `cleanupStaleProducts`가 매 반복 `rows.first()`만 다시 골라 체크해 잔여 상품이 2건 이상이면 실행마다 1건만 지워지고 나머지가 누적되는 멱등 버그가 있었다(리뷰 LOW-B). **pre-seed 검증**으로 고쳤다 — staging에 잔여 테스트 상품 2건을 직접 API로 선주입한 뒤 실구동시켜, `beforeAll`의 정리 로직이 선주입 2건 + 스펙 자체 상품까지 전부 지웠는지 API 재조회로 확인(`remaining E2E-상품- products: 0`, PR #158 커밋 본문). 이 방법론이 [[관리자-즉시저장-패턴]]과 나란히 `AGENTS.md` §8-6 "자기개선 루프"(2026-07-18 신설)의 근거 사례가 됐다.
- **도메인 매핑 누락은 이제 자동으로 잡힌다(2026-07-18 종결)** — 이전 버전에서는 GATE_SELF가 게이트 자신의 변경만 커버하고 "새 admin 도메인을 통째로 추가했는데 매핑에 등록을 깜빡함"은 사람 리뷰에 의존했다. `tests/admin/golden-crud-coverage.spec.ts`(PR #158)가 이 함정을 닫았다 — 위 「정본 구현」 참고.
- **「미배선 스펙 = 죽은 코드」(2026-07-23 종결, PR #203)** — 위 도메인 단위 감사(LIVE_COVERED)는 **도메인당 대표 스펙 1개**만 가리켜서, 이미 커버된 도메인에 두 번째 스펙 파일을 추가하며 yml 스텝 등록을 깜빡하면 못 잡는다. GATE_SELF도 스펙을 "실행"이 아니라 "도메인 boolean만 true"로 만들 뿐이라 무력. 실제로 신설 `admin-crud-insurance-cert.spec.ts`가 스텝 없이 머지 직전까지 갔고(codex 리뷰 CRITICAL), 파일단위 전수 감사를 만들자 **기존 미배선 1건이 더 적발**됐다 — `admin-crud-order-shipments.spec.ts`(#121 배송 묶음)가 커밋 이후 CI에서 한 번도 자동 실행된 적이 없었다. 워크플로 자신의 주석(golden-crud.yml:101-104)이 정확히 이 실패모드를 경고하고 있었는데도 걸렸다.
- **파이프가 종료코드를 삼킨다** — `npx playwright test ... | tail -N && git commit`은 파이프 마지막 명령(tail)의 exit 0이 전체 판정이 돼 **테스트 실패가 가려진 채 커밋이 진행**된다(PR #203에서 실측 — "GREEN 확인" 오보고의 원인). 검증 명령은 파이프 없이 exit code를 변수로 직접 받아 분기할 것.
- **Supabase signed URL은 CDN 캐시라 "파기 검증"에 못 쓴다(2026-07-23 실측)** — 파기 전 그 URL을 한 번이라도 조회했으면 원본(스토리지)이 지워져도 캐시본이 200으로 계속 응답하고, 쿼리 cache-buster로도 우회되지 않는다(캐시 키가 쿼리를 무시). 파일 파기의 진실은 service-role `storage.from(bucket).list()`로 직접 확인해야 한다 — `admin-crud-insurance-cert.spec.ts`는 이를 `SUPABASE_SECRET_KEY` 존재 시에만 조건부 실행(CI 미주입 환경 graceful skip, yml에 `STAGING_SUPABASE_*` 시크릿 배선은 완료).

## 배제된 접근 (dead-end)
- **매번 전체 e2e를 모든 PR에서 실행** — 무관한 도메인 PR까지 실행 시간이 늘고 staging DB에 불필요한 쓰기(합성 데이터 생성/삭제)가 쌓여 다른 CI 잡(payments-routes 등)의 재고·데이터 가정과 충돌 위험이 커진다. 변경-매핑 방식으로 대체.
- **nightly cron으로 정기 전체 스윕** — `deployment_status` 트리거는 실행 중인 배포의 환경 URL을 이벤트 payload에서만 얻는데, cron에는 그 payload가 없어 "최신 main preview URL"을 안정적으로 재해석할 방법이 마땅치 않았다(`golden-crud.yml:294-299`) — 필요해지면 `update-baselines.yml`의 "Resolve preview URL"(gh api deployments 조회) 이식을 전제로 재검토, 현재는 수동 `workflow_dispatch(all=true)`로 대체.

## 순위/자동화 공통 완료 게이트 — history 적재 read-back (2026-08-17)

셀러메이트 순위 파이프라인에서 **검증 완료**는 실행 신호가 아니라 정본 history 적재로만 판정한다. PC 웹 러너와 Android/ADB 모바일 러너에 예외 없이 동일 적용한다.

### 정본 구현 보강

- 웹 쇼핑 저장: `sellermate_naver_place_all/rank-check/utils/save-rank-to-slot-naver.ts:268-316` — history INSERT와 저장 실패 경고.
- 웹 플레이스 저장: `sellermate_naver_place_all/place-check/utils/save-rank-to-slot-place.ts:73-104` — place history INSERT와 결과 처리.
- 모바일 저장: `sellermate_naver_place_all/rank-check/android-app/app/src/main/java/com/navertraffic/rankchecker/SupabaseApi.kt:97-132` — 동일한 Naver history endpoint POST 후 큐 정리.
- read-back 진단: `sellermate_naver_place_all/rank-check/test/_check-history-continuity.ts:29-82` — 최근 history 건수·고유 슬롯·최신 샘플을 정본 테이블에서 재조회.

### 판정 절차

1. 작업의 정본 history 테이블과 대상 식별자 목록을 먼저 확정한다.
2. 저장 후 history를 재조회하여 대상 식별자, 저장 시각, 기대 건수 또는 원본·대상 ID 목록을 대조한다.
3. 대조가 맞을 때만 완료·성공으로 보고하고, 아니면 실패/미완료로 남긴다.

### 이름 붙인 실패 패턴

- **프로세스 생존=완료** — 프로세스·heartbeat가 살아 있어도 history가 없으면 데이터 결과는 없다.
- **INSERT 응답=적재 확인** — 웹 저장 함수는 history 오류를 경고로 남기고 계속 반환할 수 있고(`save-rank-to-slot-naver.ts:298-316`), 모바일도 POST callback만으로 성공 로그를 남길 수 있다(`RankWorkerService.kt:130-141`). 반드시 DB read-back을 추가한다.
- **큐 삭제=저장 성공** — 큐 선점·삭제는 작업 흐름 신호이지 history row의 존재 증명이 아니다.
