# 유입수-집계되는-진입
> 자동화된 상품 진입이 판매자 분석에서 **유입수(방문)로 집계되려면 실제 터치 제스처여야 한다** — `loadUrl()` 같은 프로그램적 이동은 페이지뷰만 남기고 유입에서 누락된다.

## 무엇 / 언제 쓰나

봇이 검색 결과에서 상품 상세로 들어갔는데 **판매자 분석(네이버 비즈어드바이저)에는 페이지뷰만 오르고 유입수가 0**일 때. "트래픽은 나갔는데 고객이 안 들어온 것으로 잡히는" 상황의 원인과 해법.

핵심 인과: 앵커의 `href` 를 뽑아 WebView 에 직접 로드하면 **사용자 제스처가 없는 내비게이션**이라 앵커 클릭 이벤트가 발생하지 않는다. 네이버는 이 진입을 페이지뷰로만 계산하고 유입(방문 세션 시작)으로 세지 않는다.

## 정본 구현 (canonical)

- `naver_turafic_samsung/android/SamsungTrafficBot/app/src/main/java/com/navertraffic/samsung/strategy/SamsungWebViewManager.kt:466` — `clickMidLink()`. 스캔이 돌려준 좌표가 있으면 **실제 탭이 1순위**(`:485` `캐러셀 실제 탭` 로그), 좌표를 못 구한 경우에만 `href` 직접 로드로 폴백하며 `:492` 에서 `유입 미집계 위험` 을 남긴다. 탭 직전 `pageLoad` 를 리셋해 탭이 유발한 내비게이션을 기다린다.
- `naver_turafic_samsung/android/SamsungTrafficBot/app/src/main/java/com/navertraffic/samsung/strategy/NaverPageScripts.kt:395` — 스캔 JS 가 `['found', method, href, centerX, centerY]` 를 반환한다. `scrollIntoView({block:'center'})` 후 `getBoundingClientRect()` 로 계산하므로 **좌표는 항상 확보**된다 = 폴백 경로로 샐 일이 없다.
- `naver_turafic_samsung/android/SamsungTrafficBot/app/src/main/java/com/navertraffic/samsung/strategy/WebViewGestureEngine.kt:27` — `tapCssPoint()`. 누름 유지 `:47` `50L + Random.nextLong(0,36)`(50~85ms).

## 다른 구현 / 변형

- 접근성 서비스 경로(`ExternalSamsungBrowserSession`)는 시스템 레벨 제스처라 이 문제가 없다. 대신 WebView 를 못 쓴다.
- 사람 리듬 스크롤 상수: `HumanBrowsing.kt:123` `DOWN_MIN=300` / `:124` `DOWN_SPAN=671`(300~970px), `:126` `GLANCE_UP_ODDS=4`. 실기기 `getevent` 녹화(스와이프 16회) 실측에서 나온 값 — [[사람행동-시뮬레이션]] 참조.

## 계측 방법 (이 결론을 증명한 도구)

판매자 분석 실시간 차트를 채우는 API 를 CDP 로 가로채면 **분 단위 × 채널별** 값을 그대로 얻는다:

```
GET https://bizadvisor.naver.com/api/v1/sites/<siteId>/realtime?dataType=timeseries&service=biz_advisor
→ pv_and_interaction: [{ time, pv_on_mobile, pv_on_pc, pv_on_shopping_app,
                         num_interaction_on_mobile, ... }]
```
`num_interaction_on_*` = 유입수, `pv_on_*` = 페이지뷰. `siteId` 는 `/api/v1/bizUnits` 에서 상호명으로 찾는다.

토큰(`localStorage.neoid_access_token`)이 요청마다 회전해 `fetch()` 흉내는 **401**. 그래서 30초마다 `Page.reload()` 를 걸고 그 리로드가 정상 발급받은 요청/응답을 `Network.responseReceived` + `Network.getResponseBody` 로 **패시브 캡처**한다(토큰 위조 없음).

## 주의점 / 함정

- **「프로그램 이동은 유입으로 안 세진다」** — 이 페이지의 본 주제. `webView.loadUrl(href)` 는 빠르고 안정적이라 매력적이지만 유입 집계에서 통째로 빠진다. 실측 대비(2026-07-31, 베이비걸스샵 슬롯):
  | 진입 방식 | 유입수(모바일) | 페이지뷰(모바일) |
  |---|---|---|
  | 사람이 직접 탭 (17:33·36·37·39) | 1 / 분 | 1 / 분 |
  | 봇 `loadUrl` (17:48·18:00·18:01) | **0** | 3·3·1 |
  | 봇 실제 탭 (18:09~18:33, 79회) | **74** | 76 |
- **「성공 보고가 실제 진입과 무관」** — `StrategyAResult.detailStatus` 가 `DETAIL` 로 하드코딩돼 있어, 상세 응답이 429 여도 봇은 성공으로 보고한다. 성공률 지표로 진입 여부를 판단하면 안 된다.
- **「로컬 검증을 보스 로테이션이 막는다」** — 기기명에 하이픈이 없으면 보스로 잡혀 N건마다 IP 로테이션을 시도하는데, WiFi 환경에서는 공인 IP 가 안 바뀌어 로테이션이 영영 안 끝나고 루프가 정지한다. 검증용 기기는 **하이픈 있는 쫄병 이름**(`z90-9`)으로 띄운다. 서버 그룹 상태가 이미 ROTATING 이면 로컬 서버를 재기동해 초기화한다.

## 배제된 접근 (dead-end)

- **스크롤 제거 + 상세 1초 체류(JS 점프만으로 진입)** — 처리량은 6~10초/타로 좋아졌지만 유입수는 계속 0. 속도를 올려도 집계 문제는 해결되지 않는다는 것을 확인.
- **DOM/SVG 스크래핑으로 채널별 지표 추출** — 스코어카드는 전체 합계뿐이고 모바일/PC 구분은 라인차트에만 있다. `window.Highcharts` 없음, 접근성 데이터테이블 없음, `<title>` 은 시간축 라벨뿐. 툴팁 시뮬레이션(`Input.dispatchMouseEvent`)까지 가야 해서 폐기하고 네트워크 캡처로 전환.
- **페이지 컨텍스트에서 `fetch()` 로 API 직접 호출** — `Authorization: Bearer` 토큰이 1회성 회전이라 매번 401.
