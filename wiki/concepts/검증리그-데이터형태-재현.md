# 검증리그-데이터형태-재현
> 로컬 검증 리그는 표본 수가 아니라 프로덕션 **데이터의 형태**를 재현해야 한다. 형태가 틀리면 케이스를 늘려도 회귀를 못 잡는다.

## 무엇 / 언제 쓰나

배포 전 로컬 리그로 게이트를 세울 때. 특히 **서버가 내려주는 DTO 를 로컬 스텁이 흉내내는** 구조에서.
스텁이 필드에 "그럴듯한" 값을 넣으면 리그는 통과하는데 프로덕션은 실패한다. 실패가 재현되지 않으므로
게이트가 통과 도장을 찍어주고, 사고는 배포 후에 드러난다.

판별 질문 하나: **"이 필드에 프로덕션이 실제로 무엇을 넣는지 조회해 봤는가?"**
안 봤으면 그 리그는 아직 프로덕션을 재현하지 않는다.

## 정본 구현 (canonical)

- `naver_turafic_samsung/android/SamsungTrafficBot/app/src/main/java/com/navertraffic/samsung/data/TaskLease.kt:43`
  — `val firstKeyword = source.keyword` : 앱이 **짧은 타깃 키워드**를 1차 검색어로 받는 지점.
  긴 상품명은 바로 아래 줄에서 `productName = productName ?: productTitle ?: keywordName` 로 따로 받는다.
  **두 값의 성격이 다르다는 것이 이 사고의 전부다.**
- `adpang-production/src/lib/android-admin-server.ts:2102`
  — `const productTitle = slot?.keyword_name || row.keyword_name || null` : 서버가 `keyword_name`(긴 상품명)을
  `productTitle` 로 싣는다. 같은 응답의 `keyword` 는 순위 타깃(짧은 것)이다.
- `adpang-production/src/lib/android-admin-server.ts:2225`
  — `secondKeywords` 를 그룹 A/B 에 생성해 부착. 주석에 **"플릿이 100% A 이므로 B 로만 막혀 있으면
  기능 전체가 꺼진 것과 같다"** 는 선행 사고 기록이 남아 있다 — 같은 종류의 함정이 반복된 흔적.

## 다른 구현 / 변형

- `naver_turafic_samsung/server/lib/tasks.js` — 로컬 dev-server 의 lease 응답 생성.
  프로덕션과 필드 대응이 어긋나면 리그 전체가 거짓이 된다. **로컬 스텁을 고칠 때마다 프로덕션 쪽
  같은 필드를 열어 대조할 것.**

## 주의점 / 함정

- **"쉬운 리그"(named failure).** 스텁이 짧은 타깃 키워드 자리에 긴 상품명을 넣어두면 1번 후보가
  **항상 유효해 보인다.** 2026-08-01 실측: 활성 슬롯 568건 중 **562건이 `keyword != keyword_name`**
  인데 리그는 두 값을 같게 시드했다. 그 결과 6슬롯 18/18(100%)을 통과한 빌드가 프로덕션에서 **75%** 였다.
- **표본을 늘리는 것은 해법이 아니다.** 같은 사고를 슬롯 1개 → 6개로 늘려서도 못 잡았다.
  늘려야 하는 것은 개수가 아니라 **형태의 다양성**(빈 값·경계값·프로덕션 실제 분포)이다.
- **계기판이 사유를 안 담으면 "0건 확인"은 무의미하다.** `strategy_experiment_log.result` 는 실패 시
  `"failed"` 뿐이라 사유가 없다. 그걸 모르고 "특정 실패 0건"을 게이트로 걸면 **나올 수 없는 값을
  확인했다고 보고**하게 된다. 사유는 `android_task_leases.failure_reason` 에 있다.
- **경계값은 합성해서라도 태운다.** 실물이 0건이어도 코드 분기가 있으면 합성 케이스를 만들고
  합성이라는 사실을 리그에 명시한다.
  단 **합성 케이스가 검증하려던 분기에 실제로 도달하는지 확인할 것.** 2026-08-01 실측: "상품명이 빈 슬롯"
  합성 케이스는 DTO `validate()` 가 먼저 걷어차서 **검증 대상 분기를 한 번도 태우지 못했다**(대신 다른
  버그인 핫루프를 찾아냈다 — 몇 초 만에 249회 재리스).
- **케이스당 1회 측정으로는 회귀와 편차를 구분할 수 없다(named failure).** 2026-08-01: 10슬롯 1사이클씩
  돌려 "스크롤 도달 10/10 → 8/10, MATCH 9 → 7" 을 보고 회귀를 의심했으나, 실패한 슬롯만 **4사이클 반복**하니
  4/4 성공이었다. 같은 슬롯의 착지 판정이 측정마다 MATCH / MISMATCH / INDETERMINATE 로 갈렸다.
  **의심 지점만 3~5회 반복하는 것이 전체 스윕 재실행보다 싸고 결론이 명확하다.**

## 배제된 접근 (dead-end)

- **"쿠키·캐시 초기화가 SERP 구성을 바꿔 실패한다"** 가설 — 반증됨. 로컬 리그가 초기화를 **켠 채로**
  18/18 을 냈다. 그럴듯했고(매 타 신규 방문자 = 이상 신호) 실패 시점과도 맞물렸지만, 리그가 통제군
  역할을 해서 걷어냈다. 교훈: 리그가 틀렸어도 **반증 도구로는 쓸 수 있다** — 다만 그 리그가
  "쉬운 리그"라는 사실을 알고 해석해야 한다.
- **"시간대 교란/네이버 변화"** 가설 — 반증됨. 같은 30분 버킷에서 구버전 88% vs 신버전 48%.
  버전이 시간과 완전히 상관될 때는 **아직 업데이트 안 된 잔여 기기**가 유일한 대조군이다.
- **"레이트리밋 때문"** 가설 — 반증됨. `rate_limited_429` 가 오히려 22건 → 5건으로 **감소**했다.

## 검증된 성공

원인 교정 후 실측: 성공률 **50.6% → 75% → 93.2%**, 핵심 지표(`mid_product_not_found_after_exploration`)
15분 버킷 **98건 → 10~17건 → 3~5건**(정상치 0~1 근접). 교정 내용은 "후보 1번을 짧은 타깃 키워드에서
긴 상품명으로" 하나였다.
