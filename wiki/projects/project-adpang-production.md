- **"가용 슬롯 계산"은 슬롯별 쿼터 체크가 아니라 플릿 처리량 기반 용량계획 숫자다** — `src/lib/fleet-capacity.ts:324-367` `computeCapacity`: `가용 슬롯 = (기기당 일 성공 진입수 × 기기 대수) ÷ (슬롯당 필요 진입수 N)`, 내림. N은 테이블에서 뽑는 값이 아니라 관리자가 UI에서 입력하는 **정책값**(`page.tsx` `slotEntries` state, 기본 10) — "시스템 어디에도 슬롯별 일 타수를 강제하는 장치가 없고, 이 정책이면 몇 슬롯까지 감당 가능한가를 환산할 뿐"(`fleet-capacity.ts:7-10` 주석). 기기당 처리량은 `strategy_experiment_log`(안드로이드 봇 append-only 로그) 실측, 활성 기기는 하트비트가 아니라 창 안에 실제 로그를 남긴 기기 수로 셈(`fleet-capacity.ts:11-12` — RemoteControlService가 봇 죽어도 하트비트는 계속 보냄). "현재 배정" 슬롯 수는 별도 함수(`android-admin-server.ts:886` `countEligibleSlots`)로, `daily_target`/`success_count`는 이 필터에 전혀 안 쓰임(키워드/링크/이름 존재 + 유효 시퀀스 + 미만료만 체크) — daily_target을 available-slot 계산에 쓸 거라고 가정하면 오판. API `/api/android-admin/capacity?hours=`, UI `/coupangapp/android-admin` "가용 슬롯 계산" 표.
- **PC(turafic_update) 플릿용으로 같은 계산을 이식** — `fleet-capacity.ts`의 순수 함수(`computeCapacity`/`summarizeExperimentLogs`/`summarizeDeviceSuccessRates`)는 그대로 재사용, 데이터 소스만 교체: 기기당 처리량은 `pc_runner_events`(hostname/success/ts, [[project-turafic_update]] 참고)로 `strategy_experiment_log`(device_name/success/created_at)를 대체(`android-admin-server.ts` `getPcFleetCapacity`), "현재 배정"은 PC 러너의 실제 필터(status='작동중'+mid보유+`landing_keyword_pool` active/mid_verified, `countEligiblePcSlots`)로 별도 계산. PC는 안드로이드의 대장/쫄병(boss/soldier) 그룹 개념이 없어(호스트명이 다 독립 PC, `-`로 자르면 전부 'DESKTOP' 하나로 뭉개짐) `summarizeGroupSuccessRates`/그룹 시간대 히트맵은 안 씀 — 기기별 성공률만. 온라인 판정 임계값도 재사용 못 함: 기존 `isOnline()`은 안드로이드 하트비트 주기(2분 기준)라 PC의 5분 하트비트(`strategy-a-runner.ts` `HEARTBEAT_INTERVAL`)에 그대로 쓰면 거의 항상 오프라인으로 오판 → PC는 10분(600초) 기준을 새로 씀. API `/api/android-admin/pc-capacity?hours=`, UI 같은 페이지에 "PC 가용 슬롯 계산" 박스로 병렬 추가(안드로이드 섹션은 안 건드림).
- **`sellermate_traffic_navershopping` 큐+`claim_android_naver_task`/`report_android_naver_task` RPC가 코드상 배선은 돼 있지만 실사용은 6일째 멈춰있었다(named failure, 2026-08-16 실측)** — 큐 테이블 24,861행이 전부 `queued`(claimed=0, completed=0, expired=0), 2026-08-14부터 크론(`api/sellermate/scheduler/traffic`, 5분마다)이 계속 채우기만 함. `android_task_claims`(report 시 기록되는 테이블) 최근 행이 2026-08-10, 그마저 디바이스 1대(`z90-5`)뿐. RPC는 `naver_turafic_samsung/server/lib/tasks.js:308-320`에 정상 배선돼 있어 죽은 코드는 아니지만, 실제 디바이스 트래픽이 이 경로를 안 타고 있음 — 원인 미조사. PC 플릿을 이 큐로 옮기려던 계획(원자적 슬롯 락 공유)이 이 발견 때문에 보류됨(대신 위 "가용 슬롯 계산" 이식만 진행, 락 문제는 별개 과제로 분리).
